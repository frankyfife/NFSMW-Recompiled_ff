# Native renderer for NFSMW: feasibility study (2026-10-01)

Question: can NFSMW draw natively, as The Darkness Recomp does
(`D:\Projekte\The-Darkness-Recomp_ff`), instead of emulating the Xenos GPU
command stream?

## How The Darkness does it, and why it does not carry over 1:1

- The Starbreeze engine has its own OpenGL-style render layer. The **shaders
  ship as source** in the game data: `Darkness/System/Gl/VP.xrg`, ARB
  fragment programs, `ProgramCache.xpc`.
- The port wraps engine functions: triangle batches, transform, texture and
  palette setup. It reads their data from guest memory and draws with its own
  D3D11 renderer. GPU packets are never interpreted.
- NFSMW is different:
  - The EA engine calls the **Xbox D3D library directly**. The library is
    statically linked and has no symbols.
  - There are **no shader sources**. The game looks for
    `fx\compiled\*.fx.o`, compiled Xenos microcode.
- A Darkness-style engine-level renderer would therefore first need the EA
  engine reverse-engineered and every shader translated from microcode.

## Measured (tools/renderprobe)

**D3D library in the binary**

- One contiguous block `0x8258E5E0`–`0x825A9858`: 773 functions,
  ~27,400 PPC instructions.
- Every graphics kernel import (Vd*) is called from inside it.
- The game reaches it through **85 entry points**, from 243 game functions.
- Found with `callgraph.py`, which builds a call graph from the generated
  code, and `d3d_layer.py`.

**Hooking works without changing the SDK**

- Each generated function `sub_X` is a weak alias of `__imp__sub_X`.
- A strong `extern "C"` definition in the app replaces it for every caller,
  and the original stays callable as `__imp__sub_X`.
- `app/src/render_census.cpp` does exactly that for all 85 entry points. It is
  generated by `gen_census.py`, and its counting is switched on with
  `--render_census=true`.

**The device holds a complete shadow of the Xenos registers.** Before every
draw, the flush `sub_825A40C0` goes through 64-bit dirty masks at device
offsets 16/24/32/40/48. It writes only the changed groups as PM4 register
packets:

| Group | Xenos registers | Shadow at device offset |
|---|---|---|
| Vertex float constants | `0x4000` | +1920 |
| Pixel float constants | `0x4400` | +6016 |
| Fetch constants | `0x4800` | +1152 |
| Bool/loop constants | `0x4900` | +10112 |
| Render state | `0x2000`–`0x2380` | +11456 ff. |

The state setters are partly inline: the game writes directly into the shadow
and sets dirty bits. A native layer therefore works with **Xenos register
semantics** too, it just skips the command stream.

**Cost on the game thread**

- The sampling profiler (with public symbols from the `/DEBUG` link) measured
  driving at 60 fps:
  - The main thread ("Main XThread") is active 25.8 % of the time; the rest
    is pacing in VdSwap.
  - **About 21 % of the active time is spent in the D3D library**: draw,
    flush and PM4 building. This is a lower bound.
- On top of that comes the GPU thread, which parses the same packets again.

**Shaders**

- The shader cache (`Documents\nfsmw\cache\shaders\shareable\454107D9.xsh`)
  holds only about 51 KB of microcode.
- It recorded 86 shaders and 266 pipelines at the time. The set is small and
  fixed, so offline translation is realistic.

**What the GPU thread costs, by category** (profile while driving at 120 fps,
inclusive):

| Category | Share | With option B |
|---|---|---|
| Shared memory (write watch, uploads) | 20 % | gone: resources are known from Create/Lock |
| Bindings | 10 % | stays, simplified |
| Primitive processing (index conversion, quads) | 9 % | mostly gone |
| PM4 parsing | 9 % | gone |
| Texture cache (untiling, lookup) | 8 % | mostly gone: once at load time |
| Render target / EDRAM cache | 8 % | gone: real render targets |
| Driver (self time) | 14 % | stays |

- **Option A** saves only the PM4 share on the GPU thread, plus the ~21 % on
  the game thread. The game thread is not the bottleneck at 120 fps (the GPU
  thread is), so A brings few fps on its own.
- **Option B** removes roughly half of the GPU thread's work per frame:
  shared memory, textures, render targets, PM4 and most of the primitive
  processing. That would be about 1.5–2× more throughput. It is the much
  larger effort.

## Options

**A. Direct submission (bypass PM4, keep the Xenos backend).** Medium effort,
a few weeks.

- Replace draw, flush, resolve and swap.
- At draw time, take the dirty register groups from the device shadow and
  hand them to the D3D12 command processor directly, through our own compact
  queue instead of the PM4 ring.
- Shader translation, textures, EDRAM and resolves stay as they are.
- Gain: up to ~21 % of the game thread's active time, plus PM4 parsing on the
  GPU thread.
- Risk: synchronization the guest D3D relies on, such as ring fences,
  WAIT_REG_MEM, interrupts on swap and ZPD occlusion queries.

**B. Own renderer at API level (UnleashedRecomp style).** Large effort,
months.

- An own D3D12 renderer that reads the Xenos state from the device shadow.
- Shaders translated offline: microcode to HLSL, a small fixed set.
- Real render-target textures instead of EDRAM emulation; resolves become
  copies.
- Resources known from Create/Lock/Unlock instead of write-watch on guest
  memory.
- Gain: the CP cost largely disappears, resolution and MSAA become freely
  selectable, and motion vectors are possible later.

**C. Engine level (Darkness style).** Least suitable. It would require
reverse-engineering the EA engine, and there are no shader sources.

**Recommendation:** go for B directly, but in stages, each of which can be
verified on its own:

1. **Capture**: log the D3D calls and the device state of a frame,
   including resources from Create/Lock and render targets, and check them
   against what the CP receives.
2. **Shaders offline**: translate all shaders of the cache (`.xsh`) to HLSL
   or DXIL and compare them with the existing translator.
3. **Parallel renderer**: draw a frame natively in a second window or
   offscreen, while the emulation keeps showing the real image. That makes
   image comparisons possible without risk.
4. **Switch over** path by path: menu first, then the world.

A on its own is not worth it as a performance measure; its parts (hooks,
reading the device shadow) are part of stage 1 anyway.

## Next concrete steps

1. Name the entry points precisely by disassembling them and checking their
   arguments: SetTexture, SetStreamSource, SetIndices, SetRenderTarget,
   Clear, Resolve, Create*/Lock/Unlock, fences.
2. Determine the device layout: shadow offsets for all register groups and
   the meaning of the dirty bits (`sub_825A2AA0`, `sub_825A2C58`,
   `sub_825A2B60` write them out).
3. Prototype A for a single path: log what DrawIndexedVertices plus flush
   would send, and compare it with what the CP receives from the ring. The
   result must be identical before anything is replaced.
